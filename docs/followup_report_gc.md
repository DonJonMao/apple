# 页面后台报告停滞诊断

在冻结 r3 源码、同一 100001 条健康记录 / 10000 训练组、同一公共知识副本、同一截止瞬间 `2026-11-21T16:00:00Z` 和 `/home` 存储上复现。每次从原合成夹具新建 SQLite backup；未删组、缩减分析或调用远程模型。源码与八张原始表的等价核对见 [诊断汇总](../artifacts/followup_20261127/performance/matched-gc-diagnosis-r1.json)。

| 路径 | 本期事实 | 完整报告 |
|---|---:|---|
| 直接调用 | 24.89 秒 | 113.16 秒，已冻结 |
| Streamlit 默认配置 | 150.74 秒 | 等待 240 秒仍在问题分析，未冻结 |
| 仅关闭每次脚本后的强制 GC | 27.73 秒 | 后台 create_report 115.32 秒，已冻结并显示真实发现与图表 |

这些是诊断单次值，不能当作冷 P95 或最终页面验收。宿主为共享 aarch64 环境，OS 缓存保留，外部负载不受控。与此前 r2 后端、r3 页面 600 秒超时分别保留。

多次[实际线程栈](../artifacts/followup_20261127/performance/matched-browser-r1/worker-stacks.txt)显示进度 fragment 刷新结束后，Streamlit `ScriptRunner._on_script_finished()` 调用 `gc.collect(2)`；大对象尚为活跃状态时反复扫描，阻塞后台线程。该框架默认配置假设脚本结束时没有大量工作正在进行，与本应用每秒进度刷新和后台完整分析并存的情况不符。

仓库配置现设 `runner.postScriptGC=false`。只取消刷新结束后的额外全量扫描，Python 自动循环回收和引用计数仍开启。对照日志实际观察到 22 次自动第 2 代回收、回收 490125 个对象，未出现不可回收对象。应用仍完成全部必要阶段后才保存报告；配置不改变数据、算法、权限、冻结格式或历史内容。

诊断脚本另有一个已修正的等待错误：它把故意隐藏的 `data-hz-report-id` 标记当作应可见的元素。配置对照的后台与页面实际已成功，但脚本仍等满 240 秒；原失败回执不改写。已保存 HTML、真实文字和人工审阅截图证明所选完整 ID、冻结发现和图表已显示，**不能由此推算首次页面可交互时间**。正式浏览器基准使用“新标记已存在＋实际发现/图点＋交互结束”的原有时钟重新验收。

另外，裸后台队列诊断在 native faulthandler 第二次转储时以 139 退出，原因未确认；保留其不完整堆栈、退出回执和原始表不变证据，不将它算成功或归因于产品。后续采用 Python 层线程栈采样。

本修复解决已复现的 UI 额外停滞。约 115 秒必要冷计算仍未达到 15 秒目标；工作流共享存储与后续计算优化须在最终源码上另行测量，不能用此诊断宣布整个 R06 完成。

正式 r5 后端和浏览器三档测量现已完成，见[原始样本汇总](../artifacts/followup_20261127/performance/completion-performance-r5.md)。两压力档真实页面冷生成分别126.36/181.35秒，必要阶段、冻结与最终可交互均完成；热生成/重开达标，冷生成仍失败。新驱动另修复了旧预览尚为stale时过早结束的判定，首次失败与新样本分别保留。
