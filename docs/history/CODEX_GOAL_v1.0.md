# Codex Goal：实现 Apple Health ZIP 本地分析工具

> **将本文件作为 Codex 的 Goal / 任务目标。** 开始前必须同时阅读 `DESIGN_SPEC.md` 与 `reference_product_design_v1.0.pdf`。本 Goal 优先级高于参考 PDF 中与当前桌面阶段不一致的实现建议。

## 你的角色

你是负责把一个数据密集型健康分析原型真正做出来的资深 Python 桌面应用工程师。你需要完成代码、测试、运行说明和可复现的数据流程，不是只写方案或静态页面。

## 最终目标

实现一个**完全本地运行的 Apple Health ZIP 离线整理与分析工具**。用户在 iPhone「健康」App 导出所有健康数据 ZIP 后，在电脑上选择该 ZIP，程序能够：

1. 安全检查 ZIP 包结构。
2. 从 ZIP 内部流式读取 Apple `export.xml`，不需要用户手工解压，也不能把整个 XML 一次性读入内存。
3. 识别并解析心率、静息心率、HRV-SDNN、睡眠、Workout、WorkoutStatistics、体重、活动能量、VO₂ max、呼吸频率、腕温、营养和可选女性周期记录。
4. 把原始样本统一规范化并写入本地 SQLite。
5. 处理重复导入、重叠 ZIP、未知类型、错误记录、时间和单位问题。
6. 生成数据盘点与质量报告，按功能分别判断数据是否足够。
7. 支持导入力量训练、饮食、体重 / 围度和主观状态 CSV。
9. 使用简单的本地界面展示图表、证据、限制和数据不足提示。
10. 完成自动化测试、README、合成测试 ZIP 和实现状态报告。

## 重要范围限制

- 当前阶段**不接入 HealthKit**，不开发 iPhone / watchOS App，不做实时运动采集。
- 当前阶段**不需要精美前端**。使用 Streamlit 本地运行即可；UI 以清楚、可用、可调试为准。
- 不需要账号、云数据库、远程同步或复杂后端。
- 不需要 AI API。核心计算必须离线完成；LLM 只能作为以后可选的解释层。
- 不允许把 ZIP、XML、经期信息、原始健康样本上传任何第三方服务。
- 不允许疾病诊断、避孕 / 排卵判断、RED-S 诊断、肌肉微损伤估计、精确增肌量估计。
- 不允许使用任意加权公式生成神秘恢复分 / 代谢分 / 增肌分。

## 执行方式

### Phase 0 — 仓库检查与计划

- 先检查当前仓库结构、现有代码、Python 版本、依赖管理方式和已有测试。
- 如果仓库已有实现，先理解并复用；不要覆盖用户已有工作，不要为了套用模板重建仓库。
- 写出简短的 `IMPLEMENTATION_PLAN.md`，把任务拆成可验证阶段。
- 立即开始实现，不要只输出计划后等待确认。除非缺少实际输入文件、遇到不可恢复错误或必须获得用户授权，否则自主推进。

### Phase 1 — ZIP 检查和 Apple XML 流式解析

- 实现 `inspect`：检查 ZIP 成员、文件大小、压缩比、XML 路径、导出时间和可识别类型。
- 不要直接解压整个 ZIP。
- 使用 `ZipFile.open()` 读取 XML 流，使用安全配置的 `lxml.etree.iterparse` 或等效增量解析。
- 禁用 DTD、外部实体和网络访问；实现 ZIP Slip / ZIP bomb / 路径穿越防护。
- 解析 `Record`、`Workout`、`WorkoutStatistics`、`WorkoutEvent`、`ActivitySummary`；未知节点 / 类型登记后跳过，不得让整个导入崩溃。
- 解析 Apple 日期字符串中的 UTC offset；保留 UTC、原始 offset 和本地日期。
- 保存原始 type / value / unit / source / device / metadata；另存 canonical type 和 normalized value。
- 对大文件分批入库，及时清理 XML 节点。不要将所有解析结果先放入 Python list。
- 错误要可诊断；允许 partial import，但必须准确标记 `partial_failed`。

### Phase 2 — 数据库与重复导入

- 创建 SQLite schema、索引、migration / schema version。
- 创建 import batch，记录文件 SHA-256、导入时间、导出时间、记录数、错误数、时间跨度和未知类型。
- 同 ZIP 重导入可识别；不同 ZIP 重叠历史通过稳定 fingerprint 去重。
- 不同来源的同值样本不能粗暴合并；Workout 疑似重复只标记，不默认删除。
- 确保导入中断可恢复 / 清理；已提交数据不会因重复运行翻倍。

### Phase 3 — 数据质量与覆盖度

- 按每个 canonical type 计算时间跨度、有效日期数、样本数、最近记录、缺口、来源和覆盖率。
- 质量状态：`usable / provisional / insufficient / not_imported / stale`。
- 使用 `DESIGN_SPEC.md` 中的初始工程门槛，集中放在配置文件，UI 明确它们是产品门槛，不是医学阈值。
- 不得把没有记录解释成没有佩戴、没有睡眠、没有吃饭或没有月经。
- 不要求所有数据连续 30 天；按功能独立解锁。

### Phase 4 — 外部 CSV

- 实现力量组、每日营养、体重 / 围度、主观状态 CSV 导入。
- 使用 `templates/` 的字段作为 canonical 模板。
- 做字段校验、单位转换、错误行报告、重复导入保护。
- 饮食 `log_status` 必须支持 `complete / partial / unknown`；部分记录不能用于断言全天摄入不足。
- 力量训练动作 / 器械 / 变式 / 左右侧 / 热身组 / RIR / RPE 要分别保存。

### Phase 5 — 分析模块

至少完成：

- 数据盘点与质量报告。
- 静息心率 / HRV-SDNN 个人基线（中位数、MAD、分位数）。
- 睡眠区间清洗、睡眠时长与作息趋势。
- Workout 类型、次数、时长、距离和周趋势。
- 体重趋势（稳健斜率；原始点可见）。
- VO₂ max 趋势（明确是 Apple 估计值）。
- 力量训练同动作 / 同器械的表现趋势。
- 饮食记录完整度与已记录蛋白 / 能量汇总。
- 女性周期数据可选导入、周期事件回顾、症状与表现的描述性关联。
- Evidence Card：每个结论带事实、窗口、样本数、质量状态、限制、数据来源和算法版本。

对数据不足的模块，只展示数据缺口；不要强行产生结论。算法细节遵守 `DESIGN_SPEC.md` 第 8 节。

### Phase 6 — UI 与报告

- 使用 Streamlit 做本地页面，支持本地路径输入，不要让大型 ZIP 必须通过内存型上传控件。
- 页面至少包括：导入、数据总览、数据质量、心率 / HRV、睡眠、运动、体重、有氧、力量、营养、可选周期、报告。
- 图表优先使用日 / 周聚合，避免把数百万原始点直接绘制。
- 结论必须显示时间范围、样本量和限制。
- 生成 Markdown 报告；如实现 HTML / PDF，作为附加功能，不得延误核心流程。

### Phase 7 — 测试与交付

- 使用合成 Apple Health ZIP fixture，不能把真实用户数据放入仓库。
- 覆盖 XML、ZIP 安全、时间、单位、去重、缺失、CSV、统计边界和 UI 主流程。
- 用合成大文件验证流式解析和内存行为。
- 运行完整测试和 Ruff；修复失败，不得隐藏 / 跳过测试来制造绿色结果。
- 写 `README.md`、`IMPLEMENTATION_STATUS.md`、`AGENTS.md`。
- 在最终总结中列出：实现内容、启动命令、测试结果、尚未完成项、如何用用户自己的 ZIP 验证。

## 质量与工程约束

- 先做简单、可靠、可复算的实现。不要堆叠框架、服务、代理或过度抽象。
- 数据解析、规范化、数据库、分析和 UI 必须分层；UI 不得直接解析 XML。
- 不允许把整个 XML 载入内存；不允许在解析器里维护全量样本 list。
- 所有统计计算必须有单元测试和边界处理：空数据、单样本、MAD=0、异常值、跨午夜、时区、重复记录、缺失字段。
- 保留原始样本，派生特征带算法版本，可重建。
- 所有用户健康数据默认仅本地存储；`.gitignore` 必须排除 `data/`、ZIP、数据库、个人 CSV、报告和日志。
- 不要在日志里打印原始健康记录、经期内容、精确路线或用户身份信息。
- 不要擅自调用模型 API 或安装需要云端账户的服务。
- 代码中对未知 HealthKit type 要容错并记录，不要因新增类型崩溃。
- 不能只做 Demo：导入、存储、分析、UI 和测试必须形成真实闭环。

## Definition of Done

只有满足以下条件才算完成：

1. 在本地可以按 README 安装并启动。
2. 用户输入一个 Apple Health ZIP 本地路径即可开始检查和导入。
3. XML 以流式方式解析，支持大文件。
4. 导入报告显示记录类型、数量、日期跨度、来源、错误与未知类型。
5. SQLite 中的数据可追溯、可去重、可重新分析。
6. CSV 力量 / 营养 / 测量记录可导入。
7. 质量状态按功能独立计算。
8. 至少六类分析功能能在真实或合成数据上展示。
9. 数据不足时明确提示缺少什么，不伪造结论。
10. 不需要 AI API，离线运行完整 MVP。
11. 测试通过、Ruff 通过、README 与实现状态报告完整。
12. 附上一个使用合成数据生成的示例报告。
