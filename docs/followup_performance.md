## 隔离基线与瓶颈

Git `00a35d2` 的实际源码经 `git archive` 取到 `/tmp/healthzip-followup-baseline`，报告相关源文件与 Git 对象逐字核对。100001 条健康记录、10000 训练组的原压力库只通过 SQLite backup 复制，日期、未知条件和组数未改。公共知识两库也单独备份。输入截止为 `2026-11-22T00:00:00+08:00`，与上一轮完整报告基准相同。

这是共享 Kunpeng-920/aarch64 主机（可见 192 CPU、约 2 TB RAM），OS 文件缓存未清理；同时存在其他开发/专项任务。cProfile 会增加 Python 循环开销，因此以下是诊断，不能与未剖析的历史 142.22 秒直接作速度比，也不代表普通设备。

| 路径 | 本次诊断秒数 | 观察 |
|---|---:|---|
| 完整冷生成 | 234.58 | 必要计算、依据、正文及冻结完成 |
| 同进程再次显式生成 | 4.54 | 新报告 ID，但仍恢复完整对象 |
| 新进程重新打开 | 3.44 | 读取已冻报告，未重新生成 |
| 同进程再次打开 | 3.30 | 单次样本，不称 P95 |
| 完整审计导出（与 UI 相同 `json.dumps`） | 24.07 | 冻结对象读取、序列化及写文件 |
| 已组装审计包离线重建 | 6.22 | 另计，不包括导出；与完整 `load_report` 精确相等 |

原始阶段、热点及二进制 profile 在 [baseline-100k](../artifacts/followup_20261127/performance/baseline-100k/generation.json)、[read.json](../artifacts/followup_20261127/performance/baseline-100k/read.json) 和 [baseline-100k-audit-ui](../artifacts/followup_20261127/performance/baseline-100k-audit-ui/audit.json)。另保留第一轮使用 `json.dump` 流式逐元素写文件的探索性诊断：142.91 秒；该序列化路径与 UI 不同，不能用作 UI 的旧基线或产品预算结论。

冷生成中两次 `review_analysis` 累计约 97.0 秒，4 次底层 `analyze` 约 60.7 秒；`flatten_record` 调用 627527 次累计约 34.1 秒，JSON 编码约 33.8 秒。这支持减少重复任务规范化和上下文编码，不能只把完整展开成本转成缓存。

热生成的 `read_content` 约 4.48 秒，其中 44 次解码约 3.82 秒。每次普通打开仍读取 43 个 JSON 对象、144185950 字节（内容约 79.46 MB、current 分析约 64.72 MB）；重开进程峰值约 893.5 MiB。这是需要明确小型阅读对象、按题及按轨迹加载的直接证据。

该报告引用的唯一冻结内容共 307793060 字节；审计包 307824326 字节。正文小不代表所有冻结数据小，也不代表普通打开没有展开它们。最终仍须保留完整可追溯内容，并分别报告阅读与导出规模。

## 本轮最终验收工具

- `tools/followup_report_benchmark.py`：三个独立进程测完整生成（冷 + 30 次热，逐次新 ID）、普通打开（冷 + 30 次热）、审计导出与真正文件反序列化后的离线重建；查询追踪检查普通打开和单问题不读全量分析；源组 ID 与所有原始表内容哈希另行核对。
- `tools/followup_page_benchmark.py`：新进程首开、运行中首次周/首次月各自独立进程与原库备份，另 30 次真实导航返回；等待新的 render ID、核对真实卡片与全部所显示趋势点。实际 DOM 点击时钟与自动化等待分列，后台函数结果不替代浏览器结束时刻。
- `tools/followup_report_profile.py`：仅用于瓶颈诊断，单次结果不标 P95；新旧读取接口按签名兼容。

三档最终结果与报告实际生成/打开浏览器回执将在源码稳定后追加。实体手机/Safari、普通设备和外部模型时间尚无本轮实测。

## 本轮阶段快照检查与剩余验收

[current-smoke-100k-r1](../artifacts/followup_20261127/performance/current-smoke-100k-r1/generation.json) 是实现过程中的独立源码复制，复制前后文件哈希完全相同；测量时读取该副本，不受继续开发影响。它早于后续冷路径修复，不能冒称最新工作区或最终发布代码的性能验收。

同样的 100k 原夹具和公共知识下，阶段快照的 cProfile 冷生成为 **206.69 秒**，热生成单次 **0.0266 秒**。新进程普通打开单次 **0.00571 秒**、再开 **0.00315 秒**；每次只读取 **1 个 276046 字节**的阅读对象，没有恢复旧路径的 144 MB 全量数据。冷生成仍有 `review_analysis` 81.26 秒、`period_facts` 57.69 秒、`objective_comparison` 27.61 秒等瓶颈（相互重叠，不能相加）。没有因此宣称完整冷生成已达 15 秒。

[该阶段审计](../artifacts/followup_20261127/performance/current-smoke-100k-r1/audit.json) 仍需完整处理冻结内容：唯一对象 **312453935 字节**，UI 同口径导出 **25.58 秒**，已组装包离线重建 **6.63 秒**；重建结果与完整读取精确相等。日常读取显著变小与完整审计仍较大是两个事实。

新版后端测量工具另在同一合成冻结报告上做了[工具冒烟](../artifacts/followup_20261127/performance/runner-read-smoke-r1/read.json)：两次普通读取均未查询 `analysis_run`/`workflow_run`，主动读取 W6 只查询一个指定问题对象。这里仅有两次读取，不是 30 次 P95 通过。五个新增 Python 工具 Ruff/编译检查通过；完整压力/浏览器性能工具尚未完成最终三档实跑。
